HAS 서비스워커 브라우저 경합 조사
최신 기준: main 3617b4387e40d5a1dbda3683f42e074f622e7990
상태: 운영 반영 보류 유지. 하니스 오류 재현·수정, 실제 Chromium 10회 검증 미완료.

핵심 결과
1. 원본 하니스와 클로 보정 모두 waitForFunction(async ...)로 waiting/표식을 기다렸다. 설치된 Playwright 1.62.1의 실제 내부 callback은 async predicate를 await하지 않고 Promise 객체를 truthy로 처리한다. Promise가 false로 끝나도 재폴링하지 않는다.
2. 해당 실제 callback을 추출해 Node VM에서 실행했다. async()=>false가 호출 한 번·추가 polling 0회로 false 반환하며 대기가 끝나는 것을 확인했다. 이는 callback 동작의 검증이지 실제 브라우저 실행이 아니다.
3. 실제 후보 install을 HTML 저장 후 JS fetch 직전에서 멈춘 뒤 같은 callback을 사용하면, marker predicate가 false인데 대기가 끝나고 keys는 HTML 1개다. 삭제·재설치 0회로 클로 로그의 모양이 재현된다. 이후 설치를 풀면 JS와 표식까지 3개가 정상적으로 생긴다.
4. 따라서 로그 이름 KEYS_AT_MARKER는 완료 표식이 참으로 확인됐다는 증거가 아니다. 현재 증거만으로 '완료 캐시가 뒤로 돌아가거나 재생성됐다'고 결론낼 수 없다. 먼저 대기 버그를 제거한 하니스로 다시 관측해야 한다.

근거와 검증 범위
- 읽은 main 문서: docs/team/SW-LAB-BROWSER-REVIEW-20261112.md.
- 클로 브랜치 fc7bc54aa86d888e331671eb07176381c1e1620f의 browser-lifecycle.cjs 및 lifecycle-runs.txt를 그대로 evidence-sw-race/claude/에 보존했다. 문서는 실제 Chromium 8회 중 7회 실패, 1회 통과를 보고한다. 이는 클로 관측이며 내가 수행한 브라우저 결과가 아니다.
- 내가 확인한 Playwright: 1.62.1. 실행한 설치 파일 및 callback SHA-256은 playwright-poll-provenance.json에 있다. 클로 실행 환경의 정확한 설치 바이너리와 Playwright 버전을 별도로 대조하지는 못했다.
- 최신 main은 c7de558에서 문서 7개만 추가. 원격 파일 682개 Git blob SHA 일치·수정 0개. 기존 문서용 PNG 34개는 패키지 제외, 실행 자산 누락 없음.

install promise 독립 조사
실제 generated worker install 리스너를 VM에서 실행하고 HTML put, JS put, marker put, 마지막 verify의 digest를 각각 gate로 지연했다. event.waitUntil이 받은 Promise는 모든 지점에서 아직 pending이다. 마지막 검증까지 완료해야 resolve한다. marker가 정상 생성된 직후 자산 1개만 있다는 상태는 이 순서만으로 나오지 않는다.
순차 동일 release reinstall은 정상 완료 캐시에서 fetch/put/delete 0회로 확인됐다. 손상된 완료 캐시는 삭제하지 않고 거절한다.

별도 합성 동시 실행 반례
동일 name을 공유하는 installer A와 B를 인위적으로 동시에 시작하고 B fetch를 지연했다. A가 완료한 다음 B가 실패하면 B의 catch caches.delete(name)가 A의 완료 캐시를 지운다. 이 반례는 확인됐지만 실제 단일 SW registration에서 이런 동시 installer 실행이 가능한지는 입증되지 않았다. 일반 lifecycle job 직렬화와 구분해야 한다. 이번 7/8 로그의 원인이라고 연결할 근거는 없다. 실제 재현 없이 커널을 크게 바꾸지 않았다.

이번 변경(테스트 전용)
- async waitForFunction 제거. 호스트의 pollAsync가 probe 결과를 await하고 false면 순차 재시도한다. 멈춘 probe도 호스트 deadline으로 실패시킨다.
- waiting.state==='installed' + marker 본문==release + 정확한 자산 수/키를 같은 observation에서 확인하고 그 snapshot을 사용한다. 없는 이름으로 caches.open하여 빈 캐시를 만들지 않는다.
- 동일 바이트 update 3회에서 waiting worker 객체 동일성, 설치 상태 및 캐시 키 보존을 검사하도록 준비했다.
- 진단용 worker byte만 변경하고 manifest release는 유지해 순차 동일 release 재설치를 강제하는 시험을 추가했다. 새 waiting worker의 install-resolved-after-verify 진단과 pinned 정적 자산 재다운로드 0회, 같은 캐시 키를 검사한다.
- HAS_SW_RUNS=10으로 fresh browser/context 10회 반복 가능. 커널, generated 42자산 worker, production SW와 등록, 실제 앱 소스는 변경하지 않았다. release는 여전히 41e22f32247f88c9d1ad0ece765ff034c217d73dd77046be3f2c6e3e5eafc872.

다음 실제 브라우저 확인
1. 동일 코드/Playwright 버전을 기록하고 다음 명령을 허용 환경에서 실행:
   HAS_SW_RUNS=10 HAS_CHROMIUM_EXECUTABLE=/usr/bin/chromium node tests/sw-speed-lab/browser-lifecycle.cjs
2. 10회 모두 완전 snapshot, install-resolved-after-verify, 같은 release 재설치 자산 다운로드 0, 오프라인·손실 복구·no-claim까지 통과해야 한다. 한 번의 성공이나 표식만으로 통과 처리하지 않는다.
3. 실패 시 실제 waiting worker 상태/identity·각 snapshot·삭제 호출 주체를 관찰한다. 재설치가 겹친다고 추정하지 않는다.
4. 통과해도 이는 합성 2자산 앱이다. 실제 portfolio·다중 탭/재시작·전체 캐시 소실·구 SW 전역삭제/rollback·실기기 cold/warm 성능 검증은 별도다.
