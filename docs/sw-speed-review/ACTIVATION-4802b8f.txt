HAS SW 활성화 정체 조사 / 최신 연구 묶음
기준 main: 4802b8f03c00f14200e021ab2433cfefec0e890e
결론: 원인 미확정. 운영 반영 보류. 자동 SKIP/claim/등록 변경 없음.

1. 확인한 근거
main docs/team/SW-FULL-BROWSER-REVIEW-20261112.md와 클로 branch 463f1cfc42aa7a394fc66cd81d547ed77103d103의 하니스·원로그 8개를 읽었다. 문서는 총10회(실패6/통과4)를 보고하지만 공개된 해당 디렉터리에는 실패6개와 lifecycle 완주2개만 있다. 추가 통과2개의 원로그는 확보하지 못했다. 실패 로그는 legacy=activated, candidate=installed 대기, installing 없음과 활성화 timeout을 보여 준다. 서버 새 요청이 없다는 기록만으로 이전 fetch/response 이벤트 종료를 증명할 수는 없다. rollback 로그는 후단 rollback 시험 전에 중단되어 그 시험 성공 증거가 아니다. 실패 회차에서 뒤쪽 보존 assertion이 실행되지 않았으므로 모든 실패 회차의 자료 무손상을 보장하지 않는다.

2. 원인 가설과 이번 변경
관찰할 가설은 (a) 닫힌 문서/client 잔류, (b) 구 worker의 아직 끝나지 않은 작업, (c) 하니스 관찰 자체의 영향이다. 기존 대기 루프는 25ms 간격으로 구 active worker에 MessageChannel을 열고 메시지를 보내며 port를 닫지 않았다. 클로의 TICK도 별도 메시지를 보냈다. 이것이 정체의 원인이라고 재현한 것은 아니다. 단지 먼저 제거/분리할 수 있는 관찰 간섭 요인이다.
- 기본 passive 방식은 닫기 전에 waiting worker 객체를 기억하고, 닫은 뒤 registration의 객체 동일성·activated·waiting/installing 없음만 250ms 간격으로 읽는다. 대기 중 worker로 보내는 메시지는 0개다.
- 정상 probe는 응답·오류·timeout에서 port를 닫는다.
- closed-probe / legacy-probe 비교 모드는 활성화 관찰만 메시지 방식으로 바꾼다. 전자는 port를 닫고 후자는 대조용으로 열어 둔다. 이전 전체 하니스의 완전 복제품은 아니다.
- timeout 뒤에만 active/waiting worker를 각각 한 번 질의해 controlled clients와 includeUncontrolled clients를 기록한다. 이 진단 메시지 자체는 event를 추가하므로 이미 끝난 대기 측정과 분리한다.
- 서버는 응답 finish, 닫힘/abort, 아직 종료되지 않은 응답을 기록한다. URL query는 제외한다.
- HAS_SW_AUDIT=1은 선택적 worker fetch/response Promise 관찰이다. 기본은 0이다. body 소비 또는 실제 event 수명 종료를 확인하는 계측이 아니며, observer가 microtask/timing을 바꿀 수 있다. worker 재시작 시 기록이 초기화되므로 bootId·memoryOnly를 표시한다.
- timeout 시간은 진단 전 measurementElapsedMs로 고정하고 진단 시간은 별도로 기록한다. client/worker/server 진단은 순차·비원자적 관측이므로 같은 순간의 상태라고 해석하지 않는다.

3. SKIP 버튼 제안에 대한 안전 판단
skipWaiting()에 clients.claim()을 빼는 것만으로 기존 문서의 세대 일관성을 지킬 수 없다. W3C Activate 알고리즘은 해당 등록을 사용하는 client의 active worker를 새 worker로 교체한다. claim은 이 전환의 필수 조건이 아니다.
https://w3c.github.io/ServiceWorker/#activation-algorithm
https://web.dev/articles/service-worker-lifecycle#skip_the_waiting_phase
현재 후보는 URL로 앱 client를 판별하며 문서의 세대를 식별하지 않는다. controller가 B로 바뀌었다고 가정한 합성 시험에서 기존 HTML A의 후속 JS 요청에 B의 JS가 제공됐다. 이미 실행된 JS가 자동 교체된다는 뜻은 아니다. 실제 skipWaiting/browser 전환 재현도 아니며 활성화 정체 원인의 증거도 아니다. 3개 모형 대조시험을 보존했다.
따라서 이번에는 SKIP/강제 claim을 추가하지 않았다. 강제 전환을 검토하려면 구 문서와 요청 세대의 구분, 구 자산 유지, 전 탭 재로드 협의 및 중단/복원 안전성을 별도 설계해야 한다. 단순 버튼 하나로 대체할 수 없다.

5. 권장 실제 검증 순서
이 번들의 source를 별도 로컬 checkout에서 사용한다. 4802b8f 기준 additive patch도 제공한다. 실제 사용자 프로필 대신 하니스가 만든 새 합성 프로필만 사용한다.
먼저 기본 비간섭 관찰:
HAS_SW_ACTIVATION_MODE=passive HAS_SW_AUDIT=0 HAS_CHROMIUM_EXECUTABLE=/usr/bin/chromium node tests/sw-speed-lab/browser-full.cjs
같은 조건에서 10회 실행하며 각 전체 stdout/stderr와 exit code를 남긴다. 기본15초 또는 비교 목적의 HAS_SW_ACTIVATION_TIMEOUT_MS=90000을 명시한다. 실제 사용한 Chromium/Playwright 버전과 base/release도 함께 기록한다.
실패하면 선택적 계측을 별도 회차에:
HAS_SW_ACTIVATION_MODE=passive HAS_SW_AUDIT=1 HAS_CHROMIUM_EXECUTABLE=/usr/bin/chromium node tests/sw-speed-lab/browser-full.cjs
관찰 간섭을 비교할 때만 동일 조건의 closed-probe / legacy-probe를 사용한다. 먼저 기본 passive 결과를 얻고 불필요한 전체 조합 실행은 피한다.
- controlledClients에 앱 client가 남으면 lifecycle/언로드 잔류를 추적한다.
- 서버 pending 또는 worker pending에 항목이 남으면 실제 요청/응답 단계와 abort/timeout을 조사한다.
- 빈 pending은 event 없음의 증거가 아니며 body·worker 재시작 여부를 함께 봐야 한다.
- passive와 probe 방식의 차이는 관찰 영향의 단서일 뿐 단독으로 원인을 확정하지 않는다.
성공은 마지막 SCENARIO_ASSERTIONS_PASS_NOT_RELEASE_APPROVAL까지 도달한 회차만 센다. 앞부분 snapshot이나 활성화만으로 전체 성공 처리하지 않는다. rollback/캐시 소실은 여전히 별도 위험이며 데이터 우선순위가 먼저다.

6. 해결 방향
지금 권하는 최소안은 측정 방식을 바로잡고 실제 잔류 주체를 찾는 것이다. 요청이 원인이면 해당 요청의 상한/취소를 검토하고, 남은 client가 원인이면 탭 종료/재시작 경로를 검증한다. 새 버전 안내는 준비 상태를 알리는 데 쓸 수 있지만 강제 전환 안전성을 대신하지 않는다. 현재 자료로 실행 속도 향상이나 정체 해결을 주장하지 않는다.
