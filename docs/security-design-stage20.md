# 보안 위험·개선 순서 보고서 + 잠금·암호화·키 이전 설계 (20단계 D) — 설계만, 실제 키·비밀번호·저장소는 건드리지 않음

## 1. 현재 보안 수준 (정확히)
| 항목 | 사실 | 의미 |
|---|---|---|
| 기본 비밀번호 | 소스 코드에 기본 비밀번호 상수가 있고, 사용자가 바꾸면 localStorage `v5_pw`에 **평문** 저장. 맞으면 `sessionStorage v5_auth=1` | 실제 인증·암호화가 아니라 **화면 가림**. 소스를 보거나 개발자도구로 값을 쓰면 통과 |
| 보유·거래 데이터 | `v5_*` 키에 평문 JSON(localStorage) | 같은 브라우저 프로필·같은 출처 스크립트·기기를 빌린 사람은 읽을 수 있음 |
| API 키 | `v5_geminiKey`, `v5_alphaVantageKey` 평문 localStorage. 백업 허용 목록에는 없음(확인됨) | 키가 파일로 새지는 않으나 기기 내에서는 평문 |
| 키 전송 | URL 쿼리 5곳: Gemini 3곳(`?key=`), Alpha Vantage 2곳(`&apikey=`) | 브라우저 기록·중계·공급자 로그에 남을 수 있음. 이번 단계에서 늘지 않음(시험으로 고정) |
| 지수 조회 | Yahoo 비공식 주소 + 무료 제3자 중계 4곳(키 없음) | 조회하는 지수 목록이 중계 운영자에게 보임. 보유 종목 정보는 이 경로로 가지 않음(코드 확인) |
| 보유 종목 현재가 | 사용자 GAS 웹앱(JSONP) | JSONP는 응답 스크립트를 그대로 실행하므로 GAS 계정·배포 관리가 곧 보안 경계 |
| 저장소 공개 여부 | 공개 전환 금지 유지(지시). 비공개여도 기본 비밀번호 상수는 사실상 공개된 것으로 간주 | |

**이번 단계 변경:** 키·비밀번호·인증 구조 변경 0, 키 이동·삭제 0. 시험으로 고정한 것: ① 기본 비밀번호 값이 `portfolio_v5.html` 밖(문서·시험·도구·신규 코드)에 없음 ② 키가 URL에 실리는 지점 5곳에서 증가 없음, 신규 `has/` 코드에 키·비밀번호 접근 없음 ③ 백업 허용 목록에 비밀번호·키 없음 ④ 문서·코드에 키 형태 값 없음.

## 2. 위험과 개선 순서 (효과 대비 안전한 순)
| 순서 | 개선 | 효과 | 잠금 위험 | 승인 |
|---|---|---|---|---|
| 1 | 보안 수준 정직 표시(설정 화면에 "화면 가림 수준" 안내) | 오해 방지 | 없음 | 불필요(문구만) — 이번 단계 미적용, 요청 시 |
| 2 | 키를 "이 기기에 저장 안 함(세션 메모리)" 옵션으로 입력 | 평문 상주 제거 | 없음(기존 저장 키는 그대로) | 승인 D |
| 3 | Gemini 키를 URL이 아닌 요청 헤더(`x-goog-api-key`)로 전송(공급자 문서 확인 후) | 기록·로그 노출 감소 | 없음 | 승인 D |
| 4 | Alpha Vantage는 쿼리 방식만 지원 → 브라우저 호출 중단 또는 PC 로컬 도구로 이전 | 키 노출 제거 | 기능 일부 손실 | 승인 D |
| 5 | **암호화된 백업 파일**(AES-GCM) 옵션 | 백업 유출 대비 | 없음(평문 백업 병행) | 승인 D |
| 6 | 라이브 저장소 암호화(이중 기록 → 검증 → 평문 제거) | 기기 내 노출 감소 | **높음** | 승인 D(별도) |
| 7 | 기본 비밀번호 상수 제거 + 첫 실행 비밀번호 설정 | 소스 공개 대비 | 중간(기존 사용자 이행) | 승인 D |

## 3. 키 이전 단계 설계 (자동 삭제·이동 금지)
1. 현재 키는 **그대로 둔다**. 새 방식(세션 입력/헤더)을 추가 기능으로 먼저 제공.
2. 사용자가 직접 새 방식으로 키를 입력해 동작 확인. 이때 키는 채팅·문서·로그에 붙이지 않음.
3. 확인 후 설정 화면에 "기존 저장 키 삭제" 버튼을 **제공만** 하고, 누르기 전 "공급자 사이트에서 키를 다시 발급받을 수 있는지" 확인 문구 표시. 자동 삭제 없음.
4. 키는 백업 제외이므로, 기기 변경·초기화 시 복구 방법은 "공급자에서 재발급"뿐임을 화면에 표시.
5. 롤백: 새 방식이 안 되면 기존 저장 키 방식이 계속 동작(삭제 전까지).

## 4. 잠금·암호화 설계 (기존 사용자 접근 불능 방지)
- **암호 방식:** WebCrypto AES-256-GCM, 키는 사용자 암호에서 PBKDF2-SHA256(반복 ≥ 600,000, 무작위 salt)로 유도. 서버 없음, 오프라인 동작.
- **복구키:** 암호화를 켜는 순간 무작위 256비트 복구키를 한 번만 표시(종이·별도 안전한 곳에 보관 안내). 복구키로도 데이터 키를 풀 수 있게 이중 래핑.
- **비밀번호 분실:** 복구키 → 불가 시 사전 보관한 **평문 백업 파일**에서 복원. 둘 다 없으면 복구 불가라는 사실을 켜기 전 확인 문구로 명시.
- **기기 변경:** 암호화 백업 파일을 새 기기에서 암호(또는 복구키)로 복원.
- **오프라인:** 모든 연산은 로컬. 서비스 워커·PWA 변경 없음.
- **단계(되돌림 가능):**
  - 0단계: 평문 전체 백업 → 파싱·미리보기·복원 시험으로 **복원 가능성 먼저 확인**
  - 1단계: 암호화는 **백업 파일에만** 적용(라이브 저장소 불변)
  - 2단계: 라이브 저장소에 이중 기록(평문+암호문) 후 매 실행마다 두 값 일치 검증
  - 3단계: 사용자 승인 후에만 평문 제거. 제거 전 마지막 평문 백업 필수
- **실패 시나리오 표:** 암호 분실(복구키/평문 백업) · 복구키 분실(암호로) · 둘 다 분실(평문 백업) · 브라우저 데이터 삭제(백업 파일) · 저장 중 전원 꺼짐(이중 기록 + 복원 저널 `kst.portfolio.restoreJournal` 재사용) · 소프트웨어 버그(1~2단계에서 평문 유지로 영향 없음).
- **이번 단계 구현:** 없음(설계만). 구현은 승인 D 이후 1단계부터.

## 5. 이번 단계에서 하지 않은 것
키 입력·이동·삭제 0 · 비밀번호 변경 0 · 인증 구조 변경 0 · 서버·중계 생성 0.
