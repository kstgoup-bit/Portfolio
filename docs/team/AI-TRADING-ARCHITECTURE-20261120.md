## 0. 결론 먼저 (클로 의견)

1. **현재 HAS 구조(GitHub Pages 정적 앱 + 브라우저 localStorage + GAS 중계)에는 "우회 불가능한 위험엔진"을 둘 자리가 없다.** 브라우저 안의 코드는 기기 사용자·확장 프로그램·수정된 캐시가 모두 바꿀 수 있으므로, 브라우저에서 돌아가는 위험엔진은 *조언 필터*는 될 수 있어도 *주문 차단 장치*는 될 수 없다. 따라서 G4 이상(실제 주문)은 앱 개선이 아니라 **별도 서버·키 보관·감사 저장소를 가진 다른 시스템**을 새로 만드는 일이다(비용·보안·약관 검토 대상).
2. 순태씨 철학(곡소리 분할매수·환호 분할매도·위대한 기업 장기보유)은 **거래 빈도가 낮다**(월 수 회 수준이 자연스럽다). 자동 집행으로 얻는 이득(속도)은 작고, 잃을 수 있는 것(오주문·중복주문·키 유출·급변장 연쇄 매도)은 크다. 2029년 전후 현금흐름 보전이 우선이라면 더욱 그렇다.
3. 그래서 **클로 권고 종착점은 대안 A "참모형 + 사람 수동 주문"** 이다(2절). 이는 *권고*이며 순태씨가 결정하기 전까지 **미확정**이다(9절 1번). G4(사람 승인형 주문)는 G0~G3 증거가 쌓인 뒤 다시 판단할 *선택지*로만 남기고, G5(제한적 자동화)는 2029년 현금흐름 구간에는 권하지 않는다. 지피 안의 G0~G5 틀 자체에는 동의하며 4절에 통과 기준·우회 금지 경로를 보강했다.
4. 이미 만든 부품이 G0~G2의 상당 부분을 덮는다(1절 표). 새로 시작하지 말고 이어 붙이는 것이 맞다.

## 3. 컴포넌트와 신뢰 경계

```
[공급자들]  GAS(전달) ─┐        KIS(후보) ─┐
                       ▼                    ▼
 ┌──────────── ① 데이터 품질 게이트 (결정론, 앱 코드 고정 설정) ────────────┐
 │ 계약 검증 → 등급 U/A/B/C → 격리함(quarantine) → 신선도·달력·통화 확인   │
 └─────────────── 출력: 등급이 붙은 동결 스냅샷(B만 판단 재료) ─────────────┘
                       ▼  (읽기 전용)
 ┌── ② AI 연구/후보 제안 (비결정, 권한 없음) ──┐
 │ 재무·본질가치·반론·4단계 조사 → 검토 카드    │  ← AI는 ③의 정책을 읽을 수만 있고 쓸 수 없다
 └──────────── 출력: 제안(proposal) ────────────┘
                       ▼
 ┌── ③ 위험관리 엔진 (결정론, 버전 고정 정책, AI와 별개 코드) ──┐
 │ 정책 무결성 확인 → 한도·현금 하한·중복노출·급변 정지 → 허용/차단 + 사유 │
 └──────────── 출력: 판정(verdict) — 기본값은 '차단' ──────────────┘
                       ▼
 ┌── ④ 사람 승인 게이트 (A·B에서 항상) ──┐   대안 A: 여기서 끝. 순태씨가 증권사 앱에서 직접 주문.
 └────────────────────────────────────────┘
                       ▼  (대안 B 이상에서만 존재, 현재 미존재)
 ┌── ⑤ 주문 집행기 (별도 서버, 주문 키 단독 보유) ──┐
 │ ③의 서명된 판정 + ④의 서명된 승인 둘 다 있어야만 전송 │
 └──────────────────────────────────────────────────────┘
```

**신뢰 경계 규칙(우회 방지)**
1. ②(AI)는 어떤 경로로도 ③의 정책·한도·버전을 바꾸지 못한다. 정책 파일은 ③의 코드와 함께 배포되는 고정 자료이고, 변경은 저장소 커밋 + 지피 검토 + 순태씨 승인으로만(감사 대상).
2. ③은 ②가 보낸 텍스트를 해석하지 않는다. ②의 출력은 **구조화 필드만**(종목 식별자·방향·수량 범위·근거 ID 목록) 받고, 자유문은 표시용으로만 통과.
3. ⑤는 ③·④의 판정을 *자기 키로 다시 확인*할 뿐 아니라, **주문 직전에 ③의 서버측 정책을 현재 상태로 다시 검사**한다(8절 '주문 의도 서명 계약'). 브라우저·관리자 화면·AI가 보낸 "허용" 플래그는 신뢰하지 않는다. 대안 A에는 ⑤가 없으므로 이 조건이 자동 충족. *(G4 이상 개념설계일 뿐 구현·실주문 API 연결 없음)*
4. 관리자 화면·디버그 경로·시험 모드 플래그로 ③을 끄는 기능을 **만들지 않는다**(긴급 정지는 "멈춤" 방향으로만 존재, "해제"는 4절 복구 절차).
5. 정책이 없음·형식 오류·해시 불일치·버전 불일치·서로 모순(예: 현금 하한 > 총자산) → **차단**. "정책 없음 = 제한 없음"으로 해석하는 코드 금지.

**상태도 (데이터 게이트)**
`OPEN(판단 가능)` → (충돌·결측·지연·통화/시간 불일치) → `HALTED(사유 코드)` → (복구 체크리스트 전부 충족 + 유효기간 내 새 증거 B 등급) → `PROBATION(관찰, 판단 보류 유지, N회 연속 정상)` → `OPEN`.
새 자료 *도착* 만으로는 HALTED → OPEN 전이 없음. PROBATION 기간 N은 제안값(예: 2거래일), 순태씨 결정 필요.

## 5. 검증 방법론 (G2) — 시험 **계획**만, 이번에 실행하지 않음

**편향·누출 통제**
- 생존편향: 과거 시점의 *당시* 종목 구성(상장폐지·편출 포함)으로 후보군 구성. 현재 유니버스 400종목을 과거에 그대로 쓰면 무효 — 과거 구성 자료 출처 미확보(미검증) → 확보 전에는 백테스트 대신 **전향적 성적표**(이미 진행 중)를 1차 근거로 한다.
- 미래정보누출: 재무는 **공시 접수일 기준**(SEC filed / DART 접수일)으로만 사용, 사후 정정치 사용 금지. 가격은 그 시점에 알 수 있던 종가. advice-journal의 "조언 시각 이후 자료 거부" 규칙을 백테스트 엔진에도 동일 적용.
- 과최적화: 임계값(하락률·재무 라벨 등)은 **실행 전 문서로 고정(사전 등록)**, 변경 시 새 실험으로 취급하고 이전 결과와 합산 금지. 시도한 변형 수를 같이 보고.
- 분할·배당·환율: **일봉 전 구간이 같은 조정 기준**(6절 '조정 일관성 계약')일 때만 고점·수익률 계산, 불명확하면 보류, 배당은 총수익 기준과 가격 기준을 분리 표기, 미국 종목 원화 성과는 같은 날짜 환율로만 환산.
- 비용: 수수료·환전 스프레드·세금(해외 양도세·배당세 — 세율·공제는 공식 출처 확인 전 **미검증**)·슬리피지(호가 스프레드 + 체결 지연)·미체결(지정가 미도달). 레버리지 ETF는 운용보수·일일 재조정 경로 반영.

**평가 설계**
- 인샘플/아웃샘플 분리 + 워크포워드(롤링), 국면별(하락장·횡보·상승, 금리 급변) 별도 보고.
- 비교 기준: 기준지수 매수·보유(KR 069500, US SPY), 현금 보유, **같은 금액 정기 분할매수**(철학과 가장 가까운 단순 대안).
- 표본·불확실성: 기간별 표본 수와 부트스트랩 신뢰구간 표시, 표본 부족은 '표본 부족'으로만 표시(성적표 설계와 동일).
- 실패 기준(사전 등록 예시, 제안값): 아웃샘플 초과수익의 신뢰구간이 0을 포함 → "효과 미확인"; 최대낙폭이 기준지수보다 큰데 초과수익 없음 → "채택 안 함".
- 극단 시나리오: 2008·2020·2022형 급락, 환율 급변, 거래정지·상장폐지, 레버리지 ETF −50% 이상 경로.

## 6. 데이터 계약 (G0) — 필수 필드 제안

기존 quote-meta-contract v1.1을 확장하는 방향(새로 만들지 않음).

| 필드 | 의미 | 없을 때 |
|---|---|---|
| `provider` / `route` / `upstream` | 공급자 표시명 / 앱 고정 설정상 경로 ID / 원천 계보 | 독립성 판정 불가 → B 불가 |
| `exchange`, `symbol`, `isin`(가능 시) | 거래소·종목 식별자(심볼 변경 대비 내부 ID 매핑) | 매칭 실패 → 격리 |
| `market`, `timezone`, `tradingDate` | 시장·IANA 시간대·거래일(현지) | C |
| `priceType` | `regular-close` / `intraday` / `prev-close` | C |

| `delay` / `entitlement` | 지연 여부·권한(확인된 경우만) | '미확인' 표기 |

**조정 일관성 계약 (CR-4):** 52주 고점·하락률·기간 수익률은 계산 구간의 **모든 일봉이 같은 `adjustment` 종류·같은 `adjustmentAsOf`(또는 그 이후 이벤트 없음 확인)** 일 때만 계산한다. 구간 안에 `corporateActions`의 분할·역분할이 있는데 조정 여부가 확인되지 않거나, 같은 날짜의 수정 이력이 상충하거나, 조정 종류가 섞이면 → **보류(C)**·사유 코드·혼재 구간 표시(T3b). 원 미조정 가격과 조정 가격은 별도 열로 보관하고 덮어쓰지 않는다. 기존 main `6bb93a9`(일봉 종가 고점)는 이 계약의 부분 구현이며, 조정 기준 메타 확인은 아직 없다(미검증).

**허용오차 근거:** 0.5%는 설계 제안값(공식 근거 아님). 실제 두 공급자 관측 분포(G0 증거)로 다시 정해야 한다.
**격리함:** 충돌·이상치 자료는 원장·기준지수 기록에 섞지 않고 별도 보관 + 사유 + 해결 방법(규칙 A 같은 값 보류 정리 선례).

| 급변 시장 | 서킷브레이커·갭 | 지수 하루 변동 임계 | 긴급 정지(판단 보류) | 자동 정지, 해제는 순태씨 | T13 |
| AI 환각·근거 없는 수치 | 외부 AI 출력 | advice-guard | 거절·로그 | 클로 | T6 |
| 정책 손상 | 잘못된 배포 | 해시·버전 확인 | 전부 차단 | 클로·지피 | T7 |

**기존 철학과의 충돌 (순태씨 결정 필요)**
1. 25%/10% 한도는 현재 *명목 비중*·*경고*다. 레버리지 ETF를 명목으로 재면 QLD 10%(2배)는 나스닥100 실효 약 20%인데 10% 한도를 통과한다. → 레버리지 상품을 **실효노출로 잴지**, 레버리지 상품 전체 상한을 따로 둘지 결정 필요.
2. QQQ·QLD·개별 빅테크(MSFT·AVGO 등)가 같은 기초 위험을 공유 → 확신 종목 25%가 *기초자산 합산*에서 사실상 더 커질 수 있음.
3. "곡소리에 분할매수"와 "하루 손실·낙폭 한도에서 신규 매수 차단"은 충돌한다(곡소리 = 손실이 큰 날). **r2 수정(지피 CR-1): 우량주 예외로 강제정지를 우회하는 안은 철회한다.** 대신 한도를 두 층으로 분리한다.
   - **soft limit(완충 구간):** 경고만. 곡소리 후보는 '관찰·사람 검토' 카드로 표시 가능(대안 A에선 원래 표시뿐).
   - **hard stop(한도 초과):** 강제 정지. **위대한 기업·G1 통과 여부·AI 판단과 무관하게 모든 신규 매수·주문 판정 = 차단.** 곡소리/기업가치 확인은 '관찰·사람 검토' 목록으로만 남고 집행 허용 예외가 되지 않는다.
   - **해제 절차:** 자동 해제 없음. 사유 해소 확인 + 정해진 냉각기간(제안값, 예: 다음 거래일 이후) + 순태씨 명시 해제 기록 후에만 soft로 복귀(T13과 같은 원칙).
   - **정책 개정:** 한도 값·층 구분·예외 규칙 변경은 **순태씨 사전 명시 승인 + 새 정책 버전 + 지피·클로 재검증** 없이는 효력 없음. 정지 중 개정 시도는 무결성 위반으로 차단(T9c).
   - 철학과의 조화는 *정지 장치를 약하게* 하는 대신 **soft/hard 값을 곡소리 분할매수 여력을 고려해 순태씨가 정하는 것**으로 다룬다(9절 3번).

**2029년 현금흐름 평가 지표 (제안)**
원금 보전 확률, 최대낙폭, CVaR(하위 5% 평균 손실), 비용·세후 실질수익, **우량주 분할조정 보유량 순증**(r2 수정: 액면분할·역분할로 생긴 주식 수 변화는 `corporateActions` 비율로 환산해 제거하고, *추가 매수에 따른 순증*만 셈. 보완 지표로 ① 우량주 바스켓 **취득원가 기준 투입액**·② 바스켓 **기업가치 대비 매수 시점 위치**(곡소리 구간 매수 비율)·③ **종목 교체 회전율**과 교체 전후 품질 라벨 변화 — 주식 수만 늘리려 위험하거나 싼 종목으로 갈아타는 유인을 잡기 위함. 수량 지표는 단독으로 성과 판정에 쓰지 않는다), 현금 하한 위반 횟수·기간, 인출 순서 위험(하락장 직후 인출 시나리오), 기준지수 대비 초과성과. 실제 자산·기록은 조회하지 않았으며 수치는 합성 시나리오로만 계산한다.

## 8. 실행 신뢰성 (E) — 대안 B 이상에서만 필요, 설계만

- **멱등키:** 주문 의도 1건 = 키 1개(제안·판정·승인 ID에서 결정론적으로 생성). 키는 전송 *전에* 지속 저장소에 `PENDING_SEND`로 기록 후 전송.
- **상태 전이:** `DRAFT → RISK_OK → APPROVED → PENDING_SEND → SENT_UNCONFIRMED → ACCEPTED | REJECTED → PARTIAL → FILLED | CANCELLED | EXPIRED`. 정정·취소는 원 주문 키에 연결된 새 의도로만.
- **불확실한 응답(타임아웃·끊김·재시작):** 상태를 `SENT_UNCONFIRMED`로 두고 **브로커 측 주문·체결 조회로만 해소**. 해소 전 같은 의도의 신규 주문 **금지**(재전송 = 중복 주문 위험의 핵심). 조회도 실패하면 사람에게 넘기고 해당 종목 집행 정지.
- **대조:** 매일 브로커 체결 내역 ↔ 내부 원장 대조, 불일치 1건이면 전체 집행 정지.
- **감사로그:** 추가 전용(append-only) + 해시 체인(변경 탐지), 개인정보 최소화(계좌번호 저장 금지·마스킹), 보존기간 결정 필요.
- **키:** 주문 키는 ⑤만 보유(서버 비밀 저장소), 시세 키와 분리, 역할별 권한(조회 전용 키 우선), 정기 회전·폐기 절차, 저장소·채팅·앱·백업에 절대 미기록.
- **긴급정지:** 순태씨가 한 번에 누르는 정지(서버·브로커 측 양쪽), 정지 시 미체결 주문 취소 여부는 사전 결정. 사후 조사용 타임라인 재구성 가능해야 함.
- **주문 의도 서명 계약 (G4 이상 *개념설계만*, r2 CR-3):** ③ 위험판정과 ④ 사람 승인은 **같은 주문 의도 문서 하나**에 서명한다. 서명 대상 필드: `intentId`, `nonce`(재사용 방지), `account`(마스킹 식별자), `market`, `symbol`/내부 ID, `side`(매수/매도), `qtyMax`(수량 상한), `price`·`priceLimit`과 `currency`, `orderType`, `quoteSnapshotHash`·`quoteAsOf`(시세 스냅샷과 기준시각), `policyVersion`·`policyHash`, `approver`(승인 주체), `issuedAt`·`expiresAt`. ⑤는 전송 직전에 ⓐ 두 서명이 **같은 바이트의 의도 문서**인지 ⓑ 만료·nonce 미사용 ⓒ 시세 스냅샷 신선도 ⓓ 서버 현재 정책 버전 = 서명된 버전 ⓔ 서버측 정책으로 **위험 재검사** 결과 허용 ⓕ 강제정지·긴급정지 아님 ⓖ 원장 대조 일치를 모두 확인한다. 하나라도 어긋나면(값 변경·정지·만료·재사용·버전 불일치·원장 불일치) **차단**하고 로그. 브라우저·AI·관리자 화면의 허용 플래그는 입력으로 받지 않는다. 부정 시험 계획 T15~T19. **이번 단계에서 구현·키 생성·실주문 API 연결 없음.**
- **브로커 주문 API의 멱등성 지원·조회 API·약관상 개인 자동화 허용 여부: 미검증**(이번에 공식 문서 확인 안 함 — G4 진입 시 필수 조사 항목).
