# HAS 카드 없는 KIS 인증 후보 개발 결과

작성일 2026-11-10 UTC. 작성 다비. 사용자와 클로의 후속 검토를 위한 소스 보고서다.

## 현재 결론

Workers Free와 Firebase Spark의 Google 로그인은 카드 없는 후보로 유지할 수 있다. 이번에는 이 구성을 위한 **분리된 합성 인증·호출제한 코드와 반례 시험**을 만들었다. 실제 Google 로그인이나 KIS 시세 연결을 완료한 것은 아니다. 기본 Worker는 언제나 503으로 차단되며, 환경 변수나 실제 키를 넣어도 활성화되지 않는다.

기존 앱, GAS, 투자 원장, 백업과 신호 코드는 변경하지 않았다. 별도로 확인한 일일기록 수익률·지수 갱신 결함은 이 패치에서 수정하지 않았으며, 관련 검토를 함께 제공한다. 따라서 이 전체 소스가 운영 준비 완료라는 뜻도 아니다.

## 구현한 합성 경계

1. **서버 인증 계약**: synthetic 프로젝트와 허용 UID, 정확한 발급자·대상, RS256 서명, `kid` 타입, 만료·발급·로그인 시각을 검증한다. 중복 JSON 키, 과도한 크기·깊이, 비정상 UTF-8과 알고리즘 혼동은 거절한다. 공개키 선택은 서버 주입 경로만 허용하며, 비동기 검증 후에도 시계와 키 유효기간을 다시 검사한다.
2. **전역 제한 모델**: 하나의 upstream 자격증명에 하나의 영속 직렬화 트랜잭션 상태가 있다는 계약을 만들었다. 허용량을 먼저 저장하고 토큰 1회와 시세 1회, 총 2회·전체 60초·요청당 10초로 제한한다. 실패·중단·불확실한 결과에도 환불이나 자동 재시도를 하지 않는다. 저장소가 없거나 손상되면 차단한다.
3. **긴급 차단**: 서버 전용 차단 및 `auth_time` 폐기 시각을 둔다. 차단된 진행 작업은 종료 상태로 남아 차단 해제 후에도 살아나지 않는다. 이미 발송된 요청을 되돌릴 수 있다는 보장은 없으며, 이 장치는 Firebase 전체 세션 취소가 아니다.
4. **고정 조회와 출력**: 실행 가능한 목적지는 예약된 `.invalid`뿐이다. 합성 경로는 005930·KRX·KRW 한 건이며 주문·계좌·임의 URL 경로는 없다. 합성 응답은 미검증, 가격 종류 미확인, 거래소 시각 없음, 독립 검증 아님, 저장·신호 사용 금지로 반환한다. 수신시각을 시장시각으로 바꾸지 않는다.
5. **메모리 로그인 연결부**: 실제 SDK 대신 합성 어댑터만 받는다. 토큰·사용자 객체를 저장소나 로그에 쓰지 않으며, 취소·타임아웃·로그아웃 뒤 늦게 도착한 결과를 버린다. 세대별 작업 관리로 멈춘 옛 작업이 새 로그인을 막거나 새 상태를 지우지 않도록 시험했다. 참조 제거는 메모리의 안전한 영구 삭제를 뜻하지 않는다.

실제 생성한 **합성 RSA 키로 실제 WebCrypto 서명·검증**을 수행했다. Firebase 에뮬레이터의 무서명 토큰이나 실제 Google/Firebase 발급 토큰을 사용한 시험은 아니다. 실제 사용자의 키·토큰은 없었다.

## 독립 검토에서 고친 반례

- 진행 중 차단했다가 해제하면 옛 예약이 다시 완료되던 오류.
- 주입된 예외의 임의 문자열·HTTP 상태를 응답에 반사하던 오류. 고정 오류 코드와 상태만 내보내도록 했다.
- 영속 예약 직후 시계가 `NaN`이 되어도 합성 호출을 한 번 보내던 오류.
- 숫자형 JWT `kid`를 문자열처럼 받아들이던 오류.
- 응답 대기 중 로그아웃이 요청의 취소 신호를 전달하지 않던 오류.
- 추가로 비동기 시계·키 만료, 통화·가격 상한, 멈춘 클라이언트 작업과 새 작업의 충돌을 보완했다.

상세 재현과 한계는 `INDEPENDENT-REVIEW.md`, 모듈 계약은 `IMPLEMENTATION.md`를 따른다.

## 실제 연결까지 남은 일

**현재 후보는 배포 가능한 완성 인증 서버가 아니다.** 다음 항목은 별도 구현·검토가 필요하다.

1. Firebase 공식 키 수집·회전·캐시 및 실제 취소 상태 정책. 지금의 공식 키 공급자는 의도적으로 실패한다.
2. 실제 Firebase SDK의 메모리 유지·로그인·로그아웃·redirect/popup 흐름. 현재 세대별 취소 계약이 SDK의 전역 상태와 실제로 양립하는지, 모바일 저장소 제한에서 동작하는지 확인해야 한다.
3. SQLite Durable Object 네임스페이스·고정 객체 선택·실 영속성·재시도·장애·CPU 검증. 모형의 직렬화 시험은 Cloudflare 실제 전역 동작 증명이 아니다. 다른 앱이 같은 KIS 키를 쓰는 호출까지 통제하지 못한다.
4. 기존 KIS 서버 코드의 좁은 현시세 HTTP 어댑터, 비밀 주입·토큰 보관·반환값 경계 및 비밀 없는 진단. 실제 키 등록·자격증명 권한은 아직 없다. 서버의 조회 경로 제한이 underlying KIS 키의 권한 자체를 줄이는 것은 아니다.
5. 사용자의 실제 Workers Free·Firebase Spark 및 Billing 미연결 상태, KIS 이용약관·호가/시세 이용·저장·전달 권리·계정별 호출 한도 확인. 공식 클라우드 조건은 `OFFICIAL-CONDITIONS.md`에 출처와 함께 분리했다. Workers Free의 10 ms CPU에 맞는지는 미측정이다.

실제 자원 생성·설정 변경·권한 부여·실키 등록·실 호출·배포는 사전 승인이 필요하다. 카드 등록이나 유료 전환은 진행하지 않는다. 다음 실 검증을 승인받더라도 처음에는 운영 HAS와 분리한 최소 조회 파일럿으로 범위·대상·예산·중단 기준을 다시 확정해야 한다. 실제 주문·자동매매 기능은 구현하지 않는다.

## 일일기록 작업은 별도 미완료

`daily-regression-followup/README.md`는 최근 클로 검토와 추가 반례를 정리한다. 구형 수익률 전체 보류, 한 개 저장 점과 유효한 현재 평가의 비교 누락, 시작점의 범위변경 표시가 다음 구간을 막는 문제, 지수 한 날짜 충돌이 새 날짜까지 막는 문제, 백업·실행시 검증 차이, 조회 fallback 축소가 남아 있다. 기존 Dietz가 실제 선택된 시작 스냅샷 대신 요청 기간 경계를 사용해 합성 예에서 0%를 50%로 계산하는 결함도 확인했다.

이 검토에는 수정 계획과 재현 자료를 함께 넣었지만 실행 코드는 바꾸지 않았다. 보존 원칙을 유지하면서 계산 가능성·출처 경고·범위 변경을 분리하고, 지수 충돌을 날짜별로 격리하며, 날짜 전용 일봉을 모든 소비자·백업과 함께 설계해야 한다. 단순히 보류를 없애거나 허용오차 0.5%를 넣거나 임의 종가시각을 만드는 방식으로 해결하지 않는다.

## 클로 후속 검토 요청

이 자료는 사용자 경유로 전달한다. 최종 소스와 패치는 검토용이며 main 병합·배포 승인이 아니다. 우선 합성 JWT·차단·예산의 경계와 실제 SDK/DO 어댑터에 아직 없는 기능을 확인하고, 일일기록 후속 수정은 별도 변경으로 진행해 두 작업을 혼동하지 말아야 한다. 기존 파일을 덮어쓰거나 이전 보고서의 시험 수를 현재 검증 결과로 합산하지 않는다.
