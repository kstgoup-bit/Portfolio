결론
화면과 계산식은 유지하고, 보이지 않는 수익률 표의 계산 시점만 늦추는 최소안을 권합니다. 전체 앱이 몇 초 빨라졌다는 근거는 아직 없습니다. 현재 운영 서비스워커와 새 UI는 변경하지 않았습니다.

확인한 원인
main의 renderAll()은 시작/자료 갱신 때 renderAllReturnsTables()를 호출합니다. 이 함수는 실제로 보이는 전체 화면 표뿐 아니라 일반·ISA·해외·연금 표까지 다섯 개를 모두 계산합니다. 합성 자료로 초기 대시보드 한 번을 갱신했을 때 현재 평가 5회와 기간별 판정 50회가 실행됨을 확인했습니다.
기존 서비스워커의 no-store 다운로드, 차트, 브리핑 띠 비용은 그대로 남습니다. 이 후보는 그 문제까지 해결했다고 주장하지 않습니다.

변경 범위
실행 파일은 portfolio_v5.html 하나이며, 수정 지점은 두 곳입니다.
1. renderAllReturnsTables(): active인 패널의 표만 계산.
2. switchTab(): 패널 활성화 직후 현재 표를 최신 자료로 다시 계산.
장기 결과 캐시나 비동기 대기열을 추가하지 않았습니다. 같은 탭을 다시 눌러도 재계산합니다. 원래 자료 갱신·지수 응답·활동 추가/삭제 때 호출되는 경로는 유지합니다.
표 문구, 디자인, 값 계산식, 자료 쓰기, 자동 기록, 복원, 시세 API, AI 참모, 서비스워커는 변경하지 않았습니다.

측정 결과와 정확한 한계
실제 판정 모듈과 표 생성 코드를 Node v24.22.1 / JSDOM 26.1.0에서 실행했습니다. 자료는 가상 종목 41개, 계좌별 기록 170일입니다. 각 안 5회 예열 후 순서를 교차해 각 20회 측정했습니다.
- 현재 평가: 5회 → 1회
- 기간별 판정: 50회 → 10회
- 해당 표 묶음 처리 중앙값: 1382.32ms → 639.50ms
- 같은 합성 조건에서 표시된 표 HTML: 다섯 계좌 모두 이전과 동일
이 수치는 브라우저 화면 배치·앱 전체 시작·서버 통신·실제 휴대폰 측정이 아닙니다. 중앙값 차이를 휴대폰 대기시간 개선으로 환산하면 안 됩니다. 외부 리소스를 불러오지 않는 JSDOM과 추가 HTTP 차단기를 사용했으며, 별도의 네트워크 계측값은 아닙니다.
Chromium 비교 스크립트도 준비했지만 이 환경의 UNIX 소켓 생성 제한으로 실행되지 않았습니다(socket() failed: Operation not permitted). 허용된 확대 실행에서도 같은 결과여서 브라우저 성능 수치는 없습니다.

절충점
다른 계좌 표의 계산은 그 계좌를 열 때 실행됩니다. 시작·보이지 않는 표 갱신 작업을 줄이는 대신 첫 계좌 전환에서 계산 대기가 느껴질 수 있습니다. 모든 계좌를 바로 순회하면 일부 작업은 단순히 뒤로 이동한 것입니다. 실제 기기에서는 시작과 첫 계좌 진입을 함께 비교해야 합니다.

- git diff --check 및 추가 스크립트 구문 검사 통과. 저장소 비밀값 스캔 발견 0건.
- 패치가 기준 사본에 깨끗하게 적용되고 변경 파일 12개의 최종 바이트를 재현함을 확인했습니다.
